# Security

The model is not the security, permission, execution, device-authentication, or verification boundary.

Deterministic policy remains authoritative. Models cannot self-approve, downgrade risk, add permissions, revoke devices, bypass capability scopes, expose credentials, self-verify, or self-install improvements. State-changing actions retain approval requirements where policy requires them. User autonomy modes are an additional restriction for unattended execution and cannot override `REQUIRE_APPROVAL` or `DENY`.

## Personal Core and devices

Device pairing codes are single-use and expire. Device credentials are random and stored server-side only as hashes. Web credentials are issued in HttpOnly SameSite cookies; native/device-agent credentials use bearer authentication. Every authenticated API request re-checks current device revocation and scope. A revoked device loses all associated tokens.

The Personal Core defaults to `127.0.0.1`. Non-loopback binding requires configured TLS. No public exposure is created automatically. Static PWA assets may be cached; API and personal-state responses are not service-worker cached and API responses use `Cache-Control: no-store`.

## Execution and verification

Gen-1 ToolRegistry remains authoritative for Gen-1 tools with exact allow sets. Gen-2 environment adapters expose only typed, bounded capabilities. ROS2 simulation retains a separate safety controller, e-stop, bounded movement and independent state reread. Raw motor/GPIO paths remain denied.

The model-visible workspace-test boundary prefers a Gen-2 strict local Bubblewrap worker that reuses the certified fixed `python_unittest` runner and source-bundle validation while enforcing a read-only namespace root with only the disposable `/workspace` copy writable. It uses unshared user/PID/network namespaces, a cleared fixed environment, deterministic resource limits, hostile canaries, ephemeral worker identity and host-side result-history reread. The pre-existing authenticated localhost TLS worker remains configured as a separate diagnostic surface only; it is not a `workspace_test` fallback because the stricter root-write invariant fails closed. Unsafe process execution is never treated as isolated evidence.

Audit and lifecycle state are persisted. Hidden reasoning, raw credentials, and secret values are not exposed through the daily-use UI.

## Workspace test execution boundary

The model-visible `workspace_test` boundary is live accepted through the Gen-2 strict local Bubblewrap profile `SPARKLE-GEN2-WORKSPACE-STRICT/1`. The model can supply only an exact `project_name`; persisted human approval is bound to owner/goal/tool/arguments, then produces a one-use `PermissionCenter` execution grant additionally bound to owner/goal/task/step/workspace. The grant is consumed before execution, preventing replay, before the trusted Gen-2 wrapper injects Gen-1's transport-level approval flag. The worker accepts only validated UTF-8 regular-file bundles and the inherited fixed `python_unittest` operation. Runtime files are mounted read-only, the namespace root is remounted read-only, and only the ephemeral worker copy at `/workspace` is writable; host home/repository/credential paths are not mounted, external and loopback networking are denied, PID/user/network namespaces are unshared, and the environment is cleared to a fixed allowlist. Host-validated hostile canaries verify host filesystem read/write denial, workspace escape denial, secret-environment isolation, network denial, host-process isolation, and source-artifact immutability. CPU, address-space, file-size, descriptor, process, timeout, source-count/bytes, output and workspace-size bounds remain deterministic. Verification requires the ephemeral strict-worker identity, exact sandbox claims, strict-profile health/canaries and immediate independent run-history reread. Restart rotates worker identity, does not resurrect a job, retains the consumed one-time grant as revoked, invalidates old execution handles, and requires fresh approval for a new execution.

## Automation authority

Automation definitions are not permanent unrestricted grants. Gen-2 binds each automation to an owner, source goal, bounded action prompt/capabilities, risk classification, and the lower trigger definition. Creating or mutating automation state requires the normal PersonalAgent approval boundary. When an automation later launches a goal, that goal re-enters ordinary planning, permissions, approvals, execution, observation, and verification; the automation does not inherit authority to bypass those controls.

## Document security

Document sources must be regular non-symlink files inside an explicitly authorized root, with bounded input size and bounded OOXML member/uncompressed size. Unsupported or malformed content fails closed. Structured records retain classification and digest provenance; full local paths are not persisted in document records. Sensitive classifications are not injected into external-model planning context by default, and image/scanned-document semantics are not faked through the text-only model.

## Perception and stale-world safety

Perception observations are data, not authorization. Confidence does not imply verification and model output cannot override permissions, approvals, e-stop, ROS2 safety limits, or independent action verification. Robot/device identity is registered before observations are accepted; mismatched or unknown identities and malformed observations are rejected. Freshness is recomputed from the source timestamp after restart, conflicting fresh sources do not silently overwrite current world state, and integrated simulated motion requires fresh perception before the normal action gates. Physical sensor claims are never inferred from simulation provenance.

## Operations surface security

The Personal Operations Surface is read-only aggregation. Device scopes redact approval, notification, device and world-state sections when the authenticated client lacks those capabilities. Approval controls call the existing `decide_approval` and original-goal `resume` path; they do not invoke write tools directly, so exact approval scope, risk policy, verification and tracing remain authoritative. Raw approval scope, secret-named fields, secret-like credential values and hidden reasoning are excluded from the projection.

## Notification intelligence security

Notification intelligence is non-authoritative for execution: it cannot approve actions, create grants, run tools, alter robot/e-stop state, or activate providers. Candidates and decisions retain bounded source/correlation provenance while filtering secret-named fields, raw content, requested approval scope, authorization material and hidden-reasoning fields. Owner isolation applies to inspection, explanation, attention listing and state mutation. Attention priority is not execution privilege.
## Advisory NVIDIA content safety

The routed `safety` capability is advisory only. `SafetyModelRuntime` blocks external transmission for SENSITIVE, HIGHLY_SENSITIVE, and DEVICE_CONTROL classifications by default and persists only the advisory result plus provider/model/request/reference/timestamp provenance. `PolicyEngine.evaluate_with_advisory` is monotonic: safe advice cannot grant anything; flagged advice may escalate a deterministic ALLOW to REQUIRE_APPROVAL, while existing REQUIRE_APPROVAL and DENY decisions remain authoritative. Approval, secret, workspace, device-control, ROS2 and e-stop boundaries are not delegated to the model.

## Notification delivery security

Notification delivery does not create authority and cannot change Notification Intelligence decisions. Browser desktop delivery requires an authenticated Personal Core device with the existing `notifications` scope plus an explicit browser-reported permission state; the backend cannot self-grant browser notification permission. Channel result and acknowledgement callbacks are owner- and target-device-bound. PersonalAgent inspection is read-only, while delivery retry and acknowledgement are registered as state-changing capabilities and therefore use the normal Gen-2 approval path. Direct PWA acknowledgement/result callbacks remain bounded to the already-authenticated notification device scope, analogous to the existing mark-read boundary.

Desktop payloads are short bounded projections. Secret-like values are redacted, and notifications carrying SENSITIVE, HIGHLY_SENSITIVE, or DEVICE_CONTROL provenance use a generic protected title/body and only a notification reference. Raw authorization material, hidden reasoning, private prompts, requested approval scopes, and arbitrary protected application state are not copied into desktop payloads. Voice/mobile unavailable states never trigger external delivery. Revoked browser devices are treated as unavailable even if an older channel state had reported granted permission.

## Voice privacy and authorization

Voice input has no special authority. A final provider transcript is dispatched through the same `ConversationService -> PersonalAgent` boundary as typed text, so permission, risk, approval, scoped delegation grants, independent verification, device/robot policy, and e-stop behavior are unchanged. Provider-generated speech received before that PersonalAgent boundary is rejected rather than played as an authorized SPARKLE response.

Raw microphone/audio chunks are never written to the voice event/session store by default. Persisted event schemas reject raw audio and secret/token/authorization fields. SENSITIVE, HIGHLY_SENSITIVE, and DEVICE_CONTROL classifications are denied external VoiceChat transmission unless an explicit future policy changes that boundary. Provider credentials remain secret references only. The production VoiceChat adapter refuses use while the documented NVCF streaming transport is unverified; it does not guess a direct endpoint and there is no STT/LLM/TTS fallback.

## Image generation privacy and artifact safety

Image generation is a state-changing/external action and therefore uses normal Gen-2 human approval with exact tool/argument scope. Model-supplied `approved`, `approval_id`, or `grant_id` fields are rejected, and any approved prompt/size/seed/steps/classification mutation fails scope reconciliation. SENSITIVE, HIGHLY_SENSITIVE, and DEVICE_CONTROL prompts are rejected before an external provider call. Persisted artifact manifests contain a prompt SHA-256 rather than raw prompt text and never contain API keys or authorization headers.

Provider responses are untrusted: Gen-2 requires exactly one bounded artifact, strict base64, a supported JPEG/PNG signature, bounded decoded bytes, finite/integer seed metadata, and independently parses the local image container/dimensions after decoding. Generated images are passive artifacts only; their contents do not grant authority or trigger execution. Artifact files remain inside the existing private ArtifactManager root and must pass a second filesystem/digest reread before the PersonalAgent step can verify or complete.
## Connector security boundary

`ConnectorManager` is not an authorization authority. Each operation maps to the existing deterministic Gen-2 policy capability and receives `ALLOW`, `REQUIRE_APPROVAL`, or `DENY` from `PolicyEngine`. PersonalAgent connector mutations additionally require the normal exact-scope approval record. `approved`, `approval_id`, `grant_id`, `authorization_override`, tokens, cookies, and similar authority-bearing fields are rejected when supplied inside connector arguments; only trusted server-side approval objects can satisfy an approval requirement. Approval cannot compensate for missing connector authorization, wrong owner/device identity, revoked/expired state, or an unavailable adapter.

Connector state and invocation records are owner-scoped. Device-scoped connectors require a device identity on invocation and continue to rely on their existing device/safety boundary. ROS 2 commands stay behind the existing ROS2 gateway, bounded motion policy, verification, and independent e-stop; ConnectorManager adds no direct motor path. Protected `SENSITIVE`, `HIGHLY_SENSITIVE`, and `DEVICE_CONTROL` content is denied before transmission through connectors declared as external dependencies.

Connector descriptors contain only symbolic secret references such as `GOOGLE_OAUTH_TOKEN`, `MICROSOFT_GRAPH_TOKEN`, or `GITHUB_TOKEN`. Secret values are resolved outside persisted connector state. Stored invocation provenance contains provider/system identity, policy capability, request correlation, bounded result shape, external reference when safe, and verification status; it does not store credential values, access/refresh tokens, authorization headers, cookies, hidden reasoning, or raw external payloads. The original ConnectorManager cycle did not activate external OAuth flows; later connector cycles add Gmail, Google Calendar, and Google Drive authorization through owner-only protected credential references while preserving this same persistence boundary.

After restart, persisted lifecycle/authorization records remain available, but live connection/health is not inferred from persistence alone. Adapters must be registered again and health rechecked. Descriptor-only external connectors therefore remain unavailable/external-blocked after restart rather than becoming implicitly connected.

## Gmail readonly OAuth and privacy

Gmail authorization uses the existing owner-scoped ConnectorManager lifecycle plus the symbolic `SPARKLE_GMAIL_TOKEN_FILE` credential reference. The authorized provider scope is exactly `https://www.googleapis.com/auth/gmail.readonly`. OAuth access tokens, refresh tokens, client secrets, authorization codes, and Authorization headers remain outside Gen-2 persistence and planner/model context. The adapter may refresh an expired access token through Google's credential object in memory; refreshed token material is not written to Gen-2 storage. Refresh failure becomes `EXPIRED` or `REVOKED`/authorization-required state rather than false health.

The Gmail descriptor exposes only read operations. Central `gmail.read` policy remains `ALLOW / LOW`, but invocation still requires an authorized owner-scoped connector and exact read operation. A second owner cannot reuse another owner's ConnectorManager authorization or invocation history. `connector_read` rejects mutation capabilities, and the existing `connector_invoke` approval path is not used to smuggle Gmail write authority because no Gmail write capability is registered.

Mailbox minimization is enforced structurally: list requests are bounded, metadata requests use Gmail `format=metadata`, metadata headers are allowlisted and length-bounded, snippets are excluded unless explicitly requested, and full bodies are never returned by this adapter. Persisted verification contains hashes/counts and an opaque hashed account reference instead of sender addresses, subjects, message bodies, credentials, or raw Google responses. Existing external-classification restrictions continue to apply before connector transmission.
## Google Calendar read privacy boundary

Calendar authorization uses the existing owner-scoped ConnectorManager lifecycle plus the symbolic `SPARKLE_CALENDAR_TOKEN_FILE` credential reference. Access tokens, refresh tokens, client secrets, authorization codes, Authorization headers, and raw Google responses are never persisted as connector provenance. Expired access may be refreshed in memory through Google's credential object; refresh failure becomes `EXPIRED`, `REVOKED`, or authorization-required state rather than false health.

Calendar is private personal data. `CalendarReadAdapter` requests only bounded fields. Calendar summaries contain only ID, bounded summary, access role, and primary flag. Event list entries contain only event ID, calendar ID, status, bounded summary, start/end, and all-day status; exact event reads add only the bounded `updated` field. Descriptions, conference data, attendees, attachments, and private extended properties are not requested. Connector persistence stores structural verification evidence/hashes rather than private event content. Owner isolation and central `calendar.read` policy remain authoritative.
## Google Drive read privacy boundary

Drive authorization reuses owner-scoped ConnectorManager state and the external symbolic `SPARKLE_DRIVE_TOKEN_FILE` credential boundary. Access tokens, refresh tokens, client secrets, authorization codes, Authorization headers, and raw Google responses do not enter connector persistence. Expired access can be refreshed in memory by Google's credential object; refresh failure becomes expired/revoked/authorization-required state instead of false health.

Drive is private personal data. Cycle66 is metadata-only: the adapter never calls media/download/export endpoints and never requests document, spreadsheet, source-code, PDF, image, or other file contents. Persisted Drive provenance is structural only (request correlation, verification state, hashed file IDs, MIME-type counts, metadata digests, and provider operation references). File names and other private returned metadata are available only in the bounded live result/context needed for the user's request, not copied into ConnectorInvocation provenance or Operations diagnostics. Owner isolation and central `drive.read` policy remain authoritative.
## GitHub read privacy boundary

GitHub authorization uses the owner-scoped ConnectorManager lifecycle and symbolic `SPARKLE_GITHUB_TOKEN_FILE` credential reference. The PAT is not an OAuth refresh credential and no refresh semantics are invented. HTTP 401 becomes revoked authorization; forbidden/not-found/rate-limit/transport failures remain explicit connector failures. PAT values, Authorization headers, raw credential JSON, and raw GitHub responses are never persisted.

Cycle67 is metadata/discovery oriented. Repository lists expose bounded identity/status metadata; contents lists expose path/name/type/size/SHA only; issues and pull requests omit bodies/comments; workflows omit run logs. The connector never automatically downloads source files, binaries, issue/PR bodies, comments, Actions logs, or secrets. ConnectorInvocation provenance stores only structural evidence such as hashed IDs, counts, metadata digests, provider references, and verification state. Operations diagnostics expose only connector lifecycle/health state.
## Browser orchestration security boundary

Browser execution is available only when the existing Gen-1 browser acceptance record is currently verified. Gen-2 navigation uses `Gen1BrowserSession.browse()` exclusively; no direct HTTP/browser implementation exists in PersonalAgent or ConnectorManager. The first host is session-allowlisted, HTTPS/port-443/credential-free URLs are mandatory, and Gen-1 independently rejects non-public DNS results and redirects outside the session boundary. Browser sessions are owner-bound in Gen-2, interaction counts are capped, connector revocation closes the active Gen-1 session, and restart deliberately creates no resumed live browser session.

`browser.navigate` and `browser.read` are deterministic low-risk reads. `browser.interact` is CONTROL and requires existing approval semantics; model-supplied approval fields remain rejected by ConnectorManager. Side-effecting interaction kinds are not allowlisted even with approval. Gen-2 ConnectorInvocation provenance stores hashes, bounded verification evidence, and an opaque hashed browser-session reference, not visible page text, cookies, local storage, headers, passwords, session tokens, or credentials. The pre-existing Gen-1 interaction store continues to retain its bounded revisioned browse history as part of the certified execution boundary.
## Linux application-control security boundary

Cycle69 does not expose free-form command execution, privilege escalation, script/interpreter execution, package managers, service managers, network clients, destructive filesystem operations, or arbitrary executable paths. Subprocesses receive a fixed argv list, deterministic environment (`PATH`, `LANG`, `LC_ALL` only), null stdin, bounded output for inspection, and bounded timeouts. The CONTROL probe uses null stdio, is independently checked for process liveness, then is terminated/cleaned by the verifier; restart never resurrects it.

`linux.inspect` is central-policy ALLOW/LOW. `linux.execute` is CONTROL and requires the existing human approval path; model-supplied authority fields remain rejected by ConnectorManager. Device binding is authoritative: when no device ID is supplied, ConnectorManager injects the adapter's trusted bound ID, and a supplied mismatch is denied. ConnectorInvocation stores only argument/command digests, executable identity hash, policy/approval state, device reference, and verification evidence—not environment variables, usernames, raw stdout/stderr, private files, passwords, or tokens. Revocation closes the adapter and any controlled process before marking Linux revoked.
## Computer / GUI portal security boundary

Cycle70 CONTROL supports only absolute pointer move, left click, bounded pointer scroll, and explicit press/release of a small navigation-key allowlist. There is no arbitrary text injection, clipboard API, drag/drop, application launch, shell/terminal control, destructive file-manager action, account/settings change, purchase/message action, macro language, raw input-device access, or remote-host desktop control. `computer.act` remains central-policy CONTROL and requires the existing human approval record; model-supplied approval fields cannot authorize it. Approval never widens the hard-coded action allowlist.

Absolute pointer coordinates require a current verified ScreenCast frame with positive dimensions and reject negative, non-finite, and out-of-bounds coordinates. GUI actions are capped per session; clicks are rate limited. Key state is balanced, duplicate release is rejected, and close/revoke releases tracked keys before closing the portal Session. Owner/device/session identifiers are checked independently. Raw portal session handles and raw screenshot/frame bytes are not persisted; ConnectorInvocation keeps only bounded hashes/references and verification evidence. Restart creates no live portal session and old transient session references are rejected.
## Cycle71 VoiceChat protected credential resolution

Gen-2 resolves VoiceChat by the symbolic `NEMOTRON_VOICECHAT_API_KEY` reference. The finalization resolver also permits the explicitly allowlisted `NVIDIA_API_KEY` / `SPARKLE_LLM_API_KEY` references needed by the existing NVIDIA model and image routes. The default protected source is the current user's `~/.config/sparkle/gen2.env`; group/world-readable files or files owned by another user are not parsed. The VoiceChat-specific helper remains intentionally narrow and exposes only the VoiceChat reference. Existing process-environment values take precedence, and neither the source file nor any secret value is copied into repository state, logs, provider provenance, or the Gen-2 database. The shared Level-3 `SecretResolver` implementation remains untouched.

Credential availability does not authorize inference. The existing `requires_verified_transport`/`transport_verified` gate remains fail-closed. Cycle71 verified NVIDIA control-plane authentication and the provider-declared health surface but did not establish the exact hosted WebSocket streaming gateway; consequently no production transport is injected and no real microphone/provider session is started.
## Mobile connector security boundary

Cycle72 does not expose enrollment, revocation, token issuance, permission expansion, raw ADB/Fastboot commands, arbitrary application control, arbitrary push payloads, or WhatsApp. Enrollment and device authentication remain solely in `DeviceIdentityService`; device tokens remain hashed at rest. The mobile adapter exposes only opaque device references, bounded capability metadata, notification IDs, and allowlisted sync scopes. `mobile.act` is CONTROL and requires the existing human approval record; model-supplied authority fields remain rejected by ConnectorManager. Owner/device mismatch, revoked/offline identities, unavailable transports, malformed results, and failed independent target verification all fail closed.
## Master-finalization security invariants

The protected configuration resolver reads only explicitly allowlisted names from owner-only configuration and only owner-only, non-symlink credential files under the protected SPARKLE configuration root. Secret values never enter ConnectorInvocation provenance. The ROS2 runtime no longer sources a shell script through `/bin/bash -c`; it constructs a minimal deterministic ROS environment and invokes only fixed `ros2` argv operations. The only other Gen-2 subprocess-backed document tools are fixed `pdfinfo`/`pdftotext` argv calls behind document root/size/type bounds.

Self-improvement cannot propose approval/policy/verification/audit/identity/secret-exfiltration bypass capabilities and now requires tests, security review, human approval, verified deployment and verified human rollback when a deployment-specific rollback is available. Multimodal input never opens arbitrary caller-provided filesystem paths. IoT control is typed and safety-limited; MQTT topics are exact allowlisted paths with no `+`/`#` wildcards.

## Rollback and knowledge-state finalization

Rollback persistence does not create new authority. Persisted rollback records contain bounded recovery metadata and verification evidence only; execution still requires explicit approval and a trusted executor supplied by the existing policy-controlled caller. Restart never resumes an in-flight rollback: an interrupted record is reconciled to FAILED and must be deliberately retried under policy.

Cross-source WorldModel contradictions are retained as digest/provenance metadata instead of being silently erased. Resolution requires an explicit source and remains distinguishable from the observations that produced the conflict. No hidden reasoning or secret content is added to contradiction metadata.

## Native Android credential and transport boundary

The native Android client stores the Personal Core bearer credential only as AES/GCM ciphertext in private SharedPreferences. The encryption key is generated and held by Android Keystore; Android Keystore supplies the randomized IV used for encryption. Token ciphertext/IV and the enrolled device ID/name are committed atomically, immediately reread, and compared with the accepted enrollment response before the client enters paired state; startup treats any incomplete/decryption-failed tuple as unpaired. If post-201 completion fails, partial local credentials plus the consumed one-time code are cleared so the client cannot blindly replay the consumed enrollment. No bearer token is logged or exposed to the model. Local credential removal deletes the encrypted token and device identity together.

Android cleartext networking is not globally enabled. The network security policy permits cleartext only for the loopback ADB-reverse development target, and application-level URL validation restricts that exception to port 8787. Remote targets require HTTPS. The auth preferences file is excluded from Android cloud backup and device-to-device transfer.

## Browser voice boundary

PWA voice capture is an authenticated convenience client over the existing VoiceSession API, not a new authorization path. Microphone samples remain in browser memory, are capped at 30 seconds, converted to bounded 24 kHz mono PCM16 frames, and sent only through authenticated Personal Core endpoints. Personal Core does not persist raw microphone PCM. Provider transcription enters the existing ConversationService/PersonalAgent policy boundary; approval-sensitive turns return zero substantive audio while WAITING. Both generic and Operations approval endpoints persist the human decision and resume the exact pending goal before any provider FunctionResponse/authorized audio is returned. Browser playback validates the server-declared 24 kHz mono PCM16 output contract and bounds decoded response audio before playback.
