# Mobile and cross-device use

The primary cross-platform client is the responsive SPARKLE Web/PWA served by the Personal Core. The same application shell is designed for modern desktop, tablet, Android and iOS browsers. It provides conversation, task status, approvals, notifications, device management and session handoff through the central Personal Core.

A browser/PWA installation is not treated as proof of a native or physical mobile target. The separate mobile lifecycle adapter still models install -> authenticate -> execute -> persist -> reopen -> sync -> notify -> verify -> logout, and physical/emulator `mobile` acceptance remains `EXTERNALLY_BLOCKED` until a real approved target is connected and exercised.

Cross-device conversation state is central: devices attach to the same persisted `session_id`; they do not replicate the entire private database or create independent assistants. Synchronization is capability-scoped by enrolled device permissions.
## Cycle 72 bounded mobile connector

Cycle72 adds a ConnectorManager-facing `MobileDeviceAdapter` without inventing a physical-device transport. It binds only to an already-authenticated, non-revoked mobile device identity produced by the existing `DeviceIdentityService` plus a trusted injected target transport. The adapter never receives raw enrollment codes or device bearer tokens and cannot enroll, revoke, rename, expand permissions, install applications, execute arbitrary mobile commands, or implement WhatsApp.

`mobile.read` is READ/LOW and supports only `status`, `device_info`, `connection_status`, and `capabilities`. `mobile.act` is CONTROL and supports only `request_notification` by notification ID and `request_sync` for the allowlisted scopes `state`, `notifications`, `sessions`, and `task_status`; it requires the existing human approval path. Notification requests do not create a second notification-intelligence system, and sync requests do not replicate the private database: a real target must implement the existing authenticated Personal Core/device transport and independently verify the requested operation.

The Cycle72 host audit found ADB and Fastboot installed but no authorized Android device, no Fastboot target, no Android/Apple USB device, and no usable iOS client tooling. Bluetooth is available but is not treated as a mobile authentication/transport boundary. Therefore production `mobile` remains externally blocked. A future real target can be injected through the explicit `mobile_adapter` composition hook only after existing enrollment/authentication has succeeded.

## Native Android client finalization

The repository also contains the native Android client under `mobile-android/`. The post-enrollment persistence failure found during real wire testing was traced to Android Keystore AES/GCM initialization: the app supplied a caller-generated IV to a Keystore key that requires randomized encryption. That exception occurred only after Personal Core had already returned HTTP 201 and consumed the one-time enrollment code. The client now lets Android Keystore generate the IV, persists encrypted token plus device ID/name in one synchronous SharedPreferences transaction, rereads and compares the complete tuple before marking the UI paired, and keeps the request single-flight through that secure-persistence step. If any post-201 parsing or secure-persistence step fails, partial local credentials and the consumed enrollment code are cleared and the UI requires a fresh one-time code rather than replaying the consumed code. Pair/chat requests are single-flight, and forgetting local credentials clears the complete local pairing identity instead of only the encrypted token.

Native networking is also fail-closed. Cleartext HTTP is accepted only for the development ADB-reverse target `127.0.0.1:8787` / `localhost:8787`; remote Personal Core URLs must use HTTPS and may not contain URL credentials, query strings, fragments, or path prefixes. The auth SharedPreferences file is excluded from cloud backup and device transfer so ciphertext is not restored without its corresponding Android Keystore identity.

Local Android validation passes unit tests, debug APK assembly, instrumentation-test APK assembly, and Android lint. Packaged instrumented tests exercise Android Keystore credential round-trip, complete credential clearing, and restart rejection of an incomplete persisted identity. At the current finalization check, ADB and USB enumeration expose no attached Android target, so those instrumented tests and the install/restart/chat/forget/re-pair physical acceptance sequence cannot honestly be executed yet. Production `mobile` therefore remains `EXTERNALLY_BLOCKED` on physical-target evidence, not on an unresolved known Android software defect.
